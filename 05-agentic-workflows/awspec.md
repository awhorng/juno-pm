## Goal

Triage incoming tickets into defects, features, or unknown (review)

**Primary actor:** Human + Agent co-pilot

## Trigger

New ticket loaded into Jira backlog. 

## Steps & tools

**Pattern:** Planner-Executor (multi-agent, parallel)

| Step | Action | Tool / model | Guardrail |
|---|---|---|---|
| 1 | Read request, 2. diff against build spec, 3. confirm whether request is aligned with build spec or enhancement on build spec, 4. classify type, 5. move ticket to proper queue | Design library, Jira | Agent can read design library/build specs and read Teams threads.  |

**Schemas**

Jira.retrive -> {chunks:[{text,application,summary,type}]}. "Ticket is a [type] request"

**Memory (in or out of scope)**

- **Episodic:** in-scope: tool sorts to proper queue, lifetime: backlog is empty
- **Semantic:** in-scope: tool is constantly checking build spec, lifetime: indefinite. 
- **Working:** in-scope: faeture request is in-line with design library scope. 
- **External:** Jira queue limited to project area. 

## Human-in-the-loop

When the type has been properly identified, then the agent can sort into the proper queues.

## Success & failure

- **Done when:** success, failure, escalation
- **Fails safe when:** Agent can read design library/build specs and read Teams threads. 

## Self-review

- [ ] Goal is one sentence and names the value frame.
- [ ] Trigger is a precise, testable condition.
- [ ] Pattern is chosen with a defensible reason.
- [ ] At least 3 stop conditions, including escalation.
- [ ] Each memory type named (in or out).
- [ ] Every tool lists scope (read-only vs write) and a schema.
- [ ] Read/write boundaries match the AI PRD (M3).
